# Chronoa UI review — 2026-10-05

Scope: the 20 screenshots in `/tmp/chronoa-ui/`, read against the code that
produces them (`gui/window.py`, `gui/sidebar.py`, `gui/style.py`,
`gui/surfaces/*`, `settings_window/*`, `app/*.py`).

**This is a code-and-screenshot review. Nothing here has been executed.**
Every finding below is traceable to a file and line, and each one says what to
run to see it. Treat the "verify by running it" rule as still outstanding.

---

## The short version

The information architecture is good. The panel *prose* is unusually honest and
that is worth protecting. What is missing is **information scent** — nothing on
a screen tells you whether it is healthy, degraded, or broken, and so the whole
app reads as uniformly grey whether it works or not. Beyond that: one real
deadlock (the setup wizard), one dead panel (Models), one missing CSS rule
(`selected`), a duplicated header band, a missing setup button, and a lot of
wall-of-text that is honest but not scannable.

Order of work, by return:

1. Wire `app.setup` into the main window header (5 lines, unblocks 4 dead-end panels)
2. Fix `models.py` — switch button added to the wrong parent (2 lines)
3. Add the missing `.selected` CSS rule (~8 lines)
4. Add an "attention" row per surface + surface status pills (the big one)
5. Fix the header band duplication and wire `refresh`/`banner` buttons
6. Make long rows scannable (status suffix, key-value, monospace paths)
7. Content density pass: replace "(...) as claimed" with real explanation
8. Rename what is honestly named badly, collapse what is honestly duplicated

## Blocking bugs

### 1. The setup wizard has no button anywhere in the UI

`app.setup` is registered at `app/application.py:635` and mentioned in the
shortcuts window (`gui/about.py:131`, "Set Chronoa up"). There is no keybinding,
and no button. Grep for a caller in any widget: none. The main window's header
has six buttons (`gui/window.py:263-342`): sidebar, conversations, mic, quick
ask, browser, help, settings. No setup.

Meanwhile **five panels dead-end into "turn the key on in Settings, under
Privacy"**:

- `calendar.py`: *"'calendar-read-enabled' is off… turn the key on in Settings"*
- `devices.py`: *"Grant it in Settings, under Privacy."*
- `senses.py` / `privacy.py` / `skills.py`: *"settings schema does not declare
  this key"* — these are gated by keys that are **not in the schema at all**, so
  they cannot be turned on from Settings either
- `triggers.py`: *"Ask Chronoa to arm one"* — no route to a page
- `model.py` / `voice.py` / `diagnostics.py`: *"not installed — the setup
  wizard's X page installs it"*

A first-run user hits "Chronoa is not reading your calendar" and has no way to
make it read. Fix: pack an icon button wired to `app.setup` into the main header
(`gui/window.py:335-336` — add it to the `pack_end` tuple, `set_action_name`),
and give it a tooltip. The action already exists; only the control is missing.

The `settings-schema-does-not-declare-this-key` class is worse than a missing
button and is a separate bug — see item 11.

### 2. Models panel: the switch button is added to the wrong widget

`gui/surfaces/models.py:237`:

```python
empty_added = common.empty_state(...)          # -> Adw.StatusPage
switch_btn = Gtk.Button(label="Go to Available Models")
...
empty_added.append(switch_btn)                # Adw.StatusPage has no append()
```

`Adw.StatusPage` has `set_child()`, not `append()`. So the "Go to Available
Models" button is never shown — and on the fallback path it *is* a `Gtk.Box`, so
this line works there and not with Adw. The screenshot `models.png` is empty in
both views, and even if a card existed the two `Adw.ViewSwitcher` pills (both
showing 🚫 missing-glyph boxes) sit orphaned with no content, because the empty
state appended to the wrong parent.

That glyph cluster on the switcher pills is a separate confirmation: `models.png`
is the only screenshot with 🚫 icons, and that is the only panel with a
`ViewSwitcher`.

Fix: pass the button as `common.empty_state(..., child=switch_btn)` — the
signature already has a `child` parameter (`common.py:226`) and no caller uses it.

### 3. The sidebar's "where am I" marker has no style rule

`gui/sidebar.py:159-161` adds the CSS class `selected` to the open panel's row.
Grep the whole stylesheet (`gui/style.py`): there is no `.selected` rule
anywhere. The class is set and nothing reads it, so **the open panel is not
marked in the sidebar at all** — the exact regression `SidebarPage.select()`'s
docstring says it was written to fix ("the sidebar silently stopped saying where
you were"). It is silent again, in a new way.

```css
/* The open panel. Accent background, and the accent left edge so it is
   findable when the list is scrolled and the row's own background is off. */
.sidebar-row.selected {
    background-color: alpha(@accent_bg_color, 0.16);
    box-shadow: inset 3px 0 0 0 @accent_bg_color;
}
```

Add `.sidebar-row` to the rows at `sidebar.py:119-125` so the rule cannot leak
onto any other listbox row.

## The big one: nothing says "this is broken"

`machine.png` carries a red banner: *"5 of 16 machine-state senses are not
showing a reading."* Good. `diagnostics.png` says `working` / `not working` as
the leading word of a sentence, in body-text grey, in a subtitle, wrapped across
up to three lines. That is the entire visual language for health in this app.
Everything else — Senses, Machine, Voice, Model, Privacy — renders every row the
same shade of grey whether it is granted, absent, or unavailable.

Two code facts make this cheap to fix:

- `diagnostics.py:88-93` already stamps `diagnostics-row-working`,
  `-not-working`, `-could-not-determine` onto the value label — and its own
  comment says *"None of these is styled anywhere; they are markers, and saying
  so is what keeps them honest."* They should be styled. This is one CSS block.
- `senses.py` already sorts "granted first" and knows the granted count; it just
  never surfaces it as anything but a sentence.

**What to add, one row per surface, above the groups:** a single status row
reading `Ready` / `2 of 16 senses degraded` / `Not set up yet`, driven from the
same `readings` the panel already collected. libadwaita 1.5 has `Adw.StatusPage`
and `Adw.Banner` but no `Adw.StatusBar`, so a one-row `Adw.PreferencesGroup`
with a status dot is the portable answer (`common.group()` + `common.row()` is
already exactly that).

**And in the sidebar:** a coloured dot on each row that has something to report.
Right now the sidebar is a flat 20-item list where Conversation, Calendar and
Diagnostics look equally healthy. A 6px dot costs one widget per row and turns
the list into a dashboard. Sections that are entirely fine get nothing.

**Plus an attention badge on the header.** `set_can_answer()`
(`gui/window.py:553`) already computes a whole-machine health signal and
currently uses it for one line of grey text under the orb. It is exactly the
"needs you" summary the header lacks.

## The subtitle band is broken in two different ways

**Above the title bar.** In `chat.png`, `senses.png`, `machine.png`, `models.png`
and nine others, the one-line explanation renders *above* the window's title
"Chronoa" — it reads as the window's title and pushes the real title down. The
cause is `common.surface()` (`common.py:107-121`): the subtitle label is
appended to a box *above* the `Adw.ToolbarView`, so it sits above the
`HeaderBar` rather than below it.

Fix: put the subtitle **inside** the toolbar's content stack, above the content
and below the header. Or make it a `set_subtitle` on the page title so the
header grows by one line — that is the libadwaita-native answer and it keeps the
explanation visible while the user scrolls.

**Below the content.** Triggers puts its file paths *and* its "nothing is
armed" empty state *and* a footnote in that strip, in that order, so the
explanation of what the panel is is the last thing on screen. There is already
a `common.banner()` (`common.py:255`) that does the job properly and **has zero
callers**. Wire it.

**And it is never dismissible.** `voice.png` and `model.png` have a `Reload`
button that is not connected to anything. `machine.png`'s red banner has no
button either, though its text promises one: *"Each row names which and why."*
Make `common.banner()` always carry a button — `Reload` where a reload exists,
`Turn it on` where a setting exists — and give the surfaces a `back` callback
that `common.surface()` already accepts and every caller passes `None` to.

## Scannability: the prose is honest and unreadable

The panels' defining strength — every sentence says what it is reading from —
becomes the problem at length. `voice.png`'s `speaking with espeak-ng` row is 8
lines of prose where the answer is one word. `chat.png`'s Desktop panel is a
wall of six cards.

### Long text → a status suffix + a secondary label

`diagnostics.py:_row()` puts `f"{status} - {finding.detail}"` in the subtitle.
The status is the scannable part and the detail is the evidence, so they are
different kinds of information and should not be one wrapped sentence. Put the
status in a fixed-width, non-wrapping, coloured suffix
(`common.row(title, detail, suffix=status_label)` — `common.row()` already takes
`suffix`) so the left edge becomes a status column, exactly as libadwaita's own
"Never" / "Active" rows do. Then a person reads down the right edge.

Same for `machine.py`: `read at 15:14:36` is currently a subtitle fragment;
`battery` is `not read` in the subtitle. Status → suffix.

### Key-value data → a two-column grid

`machine.png`'s `power` row is six indented lines:

```
98.0% of last full charge (Wh)
21.5% wh: holds 35.34Wh of a 45.0Wh design capacity
639 charge cycles
chemistry: Li-poly
mains: AC online
```

This is tabular. `filesystems` below it is worse — a raw `df` table that is
visibly clipped mid-row at the bottom of the viewport. Give `machine.py` a
compact key/value row (label left, value right, `Gtk.Box` with
`halign=START`/`halign=END`), and render the `df` output through
`markdown_lite`'s table support if there is any, or drop the columns that are
always empty.

### Paths → monospace

`voice.png`: `en_US-lessac-medium (Lessac - clear, American (the default)). not
downloaded - the engine looks at /usr/share/piper/voices/en_US-lessac-
medium.onnx`. That path is broken mid-word by the wrap. Every path in the app
goes through `common.monospace()` (`common.py:284`) — which exists, and which
none of the surfaces use for their paths.

### Long descriptions → a disclosure row

`skills.png` and `workbench.png` show 152 rows of 4-6 line descriptions. Same
data, same filter, and the second panel adds nothing. Make the description a
`Adw.ExpanderRow`'s child (or a "Details" suffix that reveals a second line),
so the default view is one scannable line per skill: name, and one short gate
summary. This is the single biggest density win on the two largest panels.

## Content: honest, but several sentences say nothing

The house style — name the source, never claim more than the source supports —
is genuinely good and I would not weaken it. But a few sentences have drifted
into form-without-content:

| Where | Now | Why it costs |
|---|---|---|
| `models.py:132` | `"5.2 GB  ·  llm"` (ragged double space) | Use a proper separator; there is already `_size_text()` |
| `storage` row, `machine.png` | `nvme0n1 ... 476.9 GiB, non-rotational (as claimed)` | "(as claimed)" is the author's hedge, not data |
| `conversations.py` count line | `0 of 49 senses…` — senses and conversations both use "0 of N … Rows with … are first" | Same sentence template in three panels; reads as boilerplate |
| `voice.png` Kokoro row | `not in use - the sherpa-onnx program that runs Kokoro is not installed` | Then the next row says the same about Piper. Six rows, one fact. |
| `model.py` "Cloud fallback" | `not available - both gates must be open, and privacy mode is on and cloud-fallback-enabled is off` | Two gates and a setting name in one subtitle |

The fix in every case: the status word goes in the suffix (above), and the
subtitle drops to the single fact that is not already in the status.

## Naming, where the code already admits it is wrong

- **`learning.py`: `TITLE = "What it has learned"`.** Every other title is a
  noun ("Privacy", "Senses", "Inventory"). This one is a clause, and it is the
  only row in the sidebar that reads as a sentence. → **"Learning"** or
  **"Memory"** — except `memory.py` already owns "Memory", which is itself the
  confusion (see below).
- **`memory.py` (panel) vs `senses/memory.py` (the `memory` sense).** Two
  different things named Memory. The screenshot sidebar shows "What it has
  learned" for the former; rename the *panel* to **"Facts"**, which is what it
  holds.
- **`skills.py` vs `workbench.py` vs Settings' "Tool activity".** `skills.png`
  and `workbench.png` are the same 152 built-in skills plus a different header
  and a different filter placeholder. One is "the whitelist". The other is
  "built-ins + yours + the editor". Give the second a title that says it:
  **"Your skills"**, with `skills.py` renamed **"All skills"** or folded into
  Settings' Tool activity.
- **`model.py` "Model" vs `models.py` "Models".** Singular/plural across two
  adjacent sections is a trap. The singular one is really *which engine is
  answering*; rename to **"This model"** or **"Engine"**.
- **`devices.py` "Devices"** shows one row, or an empty state saying the phone
  link is off. It is not devices; it is **"Phone"**.
- **`calendar.py`** is in "This machine" but is the user's own calendar, not the
  machine's. It belongs under a "Your world" grouping with Calendar/Devices, or
  at least not next to Disks and CPU.

### Icon collisions

`model.py` and `machine.py` both use `computer-symbolic`; `skills.py` and
`inventory.py` both use `system-run-symbolic`. Adjacent rows with identical
glyphs in a sidebar make it read as a bug.

And **`learning.py` uses `ICON = "brain"`, which does not exist** — verified:
`Gtk.IconTheme.has_icon("brain")` is `False` on this system, while every other
icon in the app resolves. That row renders as a blank/missing icon. Its
`settings` counterpart has the same one; pick something that exists (checked
`True`: `weather-clear-night-symbolic` — apt for recall — or `view-list-symbolic`
if you want it boring).

## Layout and structure

### The window has two header bars

`gui/window.py:224-244` builds a `ToolbarView` with a `HeaderBar` *and* the
`SidebarPage` builds another one (`gui/sidebar.py:72-75`). In `desktop.png` you
can see both: "Chronoa" above, the conversation's own title and six buttons
below, with window controls on the second one. This is the libadwaita
`Adw.NavigationSplitView` idiom done twice.

The split view already gives the sidebar its own title area and its own back
affordance. Pick one. The cheapest correct version: drop the sidebar's
`HeaderBar` and let `SidebarPage` start with the search entry, letting the
split view paint the title. This also gives ~48px of vertical space back on
every panel — `machine.png` currently overflows.

### Sidebar: no "you are here" on the conversation, and no grouped counts

`sidebar.py:128` sets `self._chat_row = None` and never fills it. So opening the
chat — the state the window opens in — marks nothing. Once item 3's CSS exists,
add a "Conversation" row that is marked when no panel is open.

### Panels are pushed, so the sidebar stays visible

`_show_surface()` (`gui/window.py:721-756`) pushes onto an `Adw.NavigationView`
and then *un-collapses* the sidebar. So on a 1100px window, opening Diagnostics
gives you a 280px sidebar of 20 rows next to a panel you also picked from that
sidebar. Two navigations for one move. `NavigationSplitView.set_content()` with
`Adw.NavigationPage` per surface, or keep the push but collapse the sidebar and
let the panel's back arrow return you — the split view already supports this and
`SidebarBreakpoint` is there for the narrow case.

### `Adw.NavigationPage` where `Adw.PreferencesPage` is meant

Every surface is a hand-built `Adw.NavigationPage` over a `ToolbarView` of
`Adw.PreferencesGroup`s (`common.surface()`). `Adw.PreferencesPage` +
`Adw.PreferencesDialog` gets you the sticky group headers, the scroll-to-section
`ListBox`, and correct back/forward handling for free — and it is what
`settings_window/window.py:66` already uses. This is why the group headings in
`machine.png` and `diagnostics.png` scroll away: on a 9000px page you lose your
place.

It also fixes the duplicated-subtitle problem for free: `PreferencesPage`
handles title + subtitle + search + scroller as one thing.

This is the largest single change on the list, and it is the one most likely to
disturb the existing per-surface tests, which walk the built tree. Do it after
the smaller items, and expect to update ~20 test files.

### Sidebar width and search

The sidebar is ~280px of mostly-generic labels with no badges; it is carrying
very little. 240px + a status dot would give the content 60px back.
The sidebar's search filters by title/icon/key/section — it does **not** search
the panel's content, so "which panel mentions battery?" finds nothing. Worth
saying so in the placeholder ("Search panels") — which it already does. Fine.

### The header has six flat icon buttons

sidebar · conversations · mic · quick-ask · browser · help · settings, all
`symbolic` glyphs of similar weight. Nothing is grouped, nothing is labelled
except by tooltip, and the mic — the one thing a voice app's user looks for —
is a 16px `Gtk.Image` next to them, not a button. Consider: a primary "listen"
action next to the orb rather than in the header, and a `Adw.MenuButton` for
quick-ask/browser/help under an overflow.

## Repeated controls that should not be

`Reload` appears on `voice.py` and `model.py`; `Refresh` on `organs.py`;
`Filter by …` on `activity.py` and `conversations.py`; `Filter skills by name or
description` appears identically on `skills.py` and `workbench.py`. Five
near-identical search entries, four disconnected reload buttons. One reload
affordance per panel, wired, or none.

## Settings window overlaps the panel list badly

Not in the screenshots (it isn't captured), but: the settings window has
**Senses, Privacy, Tool activity, Voice, Models, System** — and the sidebar has
panels for **Senses, Privacy, Activity, Voice, Models, Model**. Two surfaces,
two places, different content, for the same jobs. Diagnostics exists in one and
not the other; Approvals and Cloud providers exist only in Settings.

Either the sidebar *is* the settings surface (fold the settings window into the
sidebar and delete the duplicate window), or the sidebar panels are all
read-only *reports* and should be titled that way. Right now a person has two
plausible places to look for the same switch, and the wrong one at least half
the time.

## Things that are right and should not change

Worth saying, because a redesign pass is exactly when these get lost:

- The **empty-state discipline**. Every panel that has nothing says why, names
  the gate, and offers the action. `devices.png`, `calendar.png`,
  `triggers.png`, `activity.png`, `conversations.png` are all good. This is the
  single best thing about the UI.
- The **per-panel source citations** (`voice.png`, `desktop.png`,
  `diagnostics.png`). Read from the module that would make the thing true,
  never from a copy.
- The **three-word diagnostics vocabulary** and the standing admission about
  what cannot be proven from outside the process.
- The **`browser` button hiding itself** when WebKitGTK is absent
  (`gui/window.py:758`) rather than opening nothing.
- The **breakpoint-driven model card reflow** (`models.py:295`) — the right
  pattern, worth copying to the machine panel.
- **`_surface_pages` caching** so a panel does not re-measure the machine every
  time it is opened.

list actually contains `selected` after `SidebarPage.select("senses")` — not
that the method was called.
