# Why docs/screenshots/main.png was not replaced

`README.md` shows `docs/screenshots/main.png`. The image is stale - it shows
six suggestion chips, a TIMERS card in the rail, and a sidebar row called
"Memory". The app as shipped is different. Replacing it with a fresh capture
was attempted and deliberately not done; this note records why, so the next
pass does not re-derive it and does not paste an image that lies.

## The two blockers, measured rather than guessed

1. **The capture could not hold the requested size.** `MAIN-UI-TODO.md`
   section 13 records the 2026-11-18 re-check: at the README's 1280x860, the
   broadway compositor capped the shot at 1024x768. A `main` page rendered at
   HEAD came back 0.2% opaque - a picture of the window frame with nothing
   inside - while the same commit at its own 460x640 rendered fully. A file
   appearing in the output directory is not evidence that the target was
   photographed; `tools/render_ui_batch.sh` now measures opacity so a frame
   around nothing fails instead of reporting PASS.

2. **The app in the capture answers from the cloud.** The capture harness runs
   the real `ChronoaApplication` in a scratch data directory with no compiled
   schema and no local model. That is not a contrived machine: it is what a
   fresh install looks like before setup, and it says *"Answering from the
   cloud"* / *"No model is answering yet"* and logs *"Falling back to cloud
   LLM providers ... Prompts will leave this machine"*. The old screenshot
   says *"Answering on this computer"*, which is the better claim for a
   local-first product but the wrong claim for that machine.

Pointing the harness at the real model directory is not free: `AGENTS.md`
records a capture that did exactly that started real services from inside the
capture - an OBEX session to the person's paired phone and a BLE advertisement
named "Chronoa Remote" - because the compiled schema turned the consent
switches on. The harness now kills its whole `setsid` process group on exit
for that reason, but a screenshot must not depend on the developer's real
hardware and accounts.

## What would make a replacement honest

A capture that (a) renders the whole main window at a size the compositor can
hold, (b) has a local model installed in its own scratch data home with no
network fallback needed, and (c) passes an opacity check above the measured
false-pass floor. Until then the stale image stays: replacing it with a
1024px, cloud-answering frame would make the README describe a product that
does not exist.

The render harness is the durable artefact; the recipe and the failure modes
are in `AGENTS.md` under "Rendering the UI to a PNG". No screenshot should be
generated by hand into `docs/screenshots/` outside that harness - a one-off
image is lost with the session and cannot be re-measured.
